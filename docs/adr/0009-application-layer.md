# 應用層隔離（多產品）

評論系統預期服務多個產品：文章評論是第一個，之後會有第二個產品接入。若所有產品共用單一命名空間，文章 key 遲早碰撞、留言間隔／每日上限／敏感字被迫全產品統一、封鎖與檢舉紀錄跨產品污染。決定在資料模型最頂層加「應用」（application）隔離單位：一個產品一個應用，key resources 按應用分開。

按應用隔離：留言（文章 key 只在應用內唯一）、emoji、靜音、檢舉、自動封禁（犯規累計按應用計）、封鎖、敏感字、系統設定（間隔／每日上限／新用戶冷卻期／自動封禁 tier）、審計紀錄。跨應用共用：用戶（前端會員系統）與操作員（Logto）——同一個人在各應用內的狀態互相獨立。

封鎖不跨應用：用戶在應用 A 被封，在應用 B 照常留言。這是刻意決定——各產品的社群標準與風險不同，由各產品自己的檢舉訊號與操作員決定，不做一次封全部的聯合封鎖。

識別字設計：應用 key 是系統產生的機器識別字，API 呼叫必帶；應用 slug 是操作員建立時設定的公開識別字（小寫英數字＋連字號、長度 3–32、全系統唯一、建立後不可改），經 API 暴露。留言的全球唯一識別是單一「留言 ID」：生成時即全球唯一（ULID），不是「應用 slug＋留言 ID」的拼接——拼接只是把組合 logic 從前端搬到後端（要生成、解析、存兩份），全球唯一 ID 則令組合 logic 在任何一方都不存在，前端拿到一個 opaque ID 即可構造 canonical URL。應用 slug 的角色是可選的 URL 可讀性前綴（前端想用就用），不參與唯一性。文章本身已有 canonical URL，每則留言也需要可分享、可索引的永久身份，由留言 ID 單獨承擔；URL 路徑結構與 domain 由前端自定，評論系統只提供穩定識別字、不擁有 URL。slug 不可改是刻意決定：識別字一換，舊連結即斷、SEO 權重分裂；產品要改的是顯示名稱（可改名），不是 slug。不採「應用 slug＋應用內流水號」拼接式公開 ID：per-app 流水號在高流量下是熱點計數器，ULID 去中心化生成、天生全球唯一。

後果：所有 API（前端＋控制台）必帶應用 key；控制台操作前先選應用；所有資料表加 application_id，unique constraint 改複合鍵（application_id＋原欄位），留言表例外——主鍵即全球唯一留言 ID（ULID）；Redis 快取 key 與批次端點（N 篇 x M 則）都以應用為範圍；雲盾設定（business ID 等）按應用配置，整合細節待補（屆時更新 ADR-0001）。

不採單一命名空間＋文章 key 前綴約定：約定無法強制，碰撞只是時間問題，且設定與封鎖仍被迫共用。不採每產品獨立部署一套：營運成本倍增、控制台要切換多個站台，違反「兩個介面、一個後端」。
